When I submitted my first contribution to an open source project, my pull request unexpectedly failed, and it turned out to be a great learning opportunity! In this post, we'll go through the steps of diagnosing and fixing this specific failure, which will teach us a bit about GitHub Actions, linting, and how to investigate pull request problems.

## The Unexpected Error

First, let's set the scene: after reading an open source project's Contributing doc, I [forked](https://docs.github.com/en/pull-requests/get-started/about-forks) the repository, made a simple change that fixed a broken link in the project's README, and then created a [pull request](https://docs.github.com/en/pull-requests/reference/pull-requests) with those changes. This result appeared in my pull request:

![Messages in a GitHub PR: "1 failing check" heading, below it a red circle with an X and the message "Pull Request Checks / Lint (pull_request)".]({{ "/assets/images/failed_PR/01-some-checks-were-not-successful.png" | relative_url }}){: .align-center}

My pull request was approved by the owner of the project, but it failed some of the required checks. In case this is your first time seeing something like this, some quick explanations are in order. If you have a project on GitHub, you can use [GitHub Actions](https://docs.github.com/en/actions/get-started/quickstart) to automate aspects of your build pipeline, such as automatically running tests against pull requests. That's exactly what has happened here, and my pull request didn't pass one of those tests.

## Workflows

Let's see if we can get some more information about this failed test. If we click the ellipses to the right of the failed check, we'll get the option to "View details", which will take us to this page:

![The GitHub Actions page showing the failed workflow run. A red circle with an X shows us that the failure occurred in the "Lint Title" section.]({{ "/assets/images/failed_PR/02-workflow-run.png" | relative_url }}){: .align-center}

This screen shows a summary of the workflow run that occurred when our pull request was created. If you're unfamiliar with workflows, you can basically think of them as a series of commands that get run in sequence whenever the workflow is triggered. It looks like everything went fine until it reached the "Lint Title" section.

Unfortunately, the error itself doesn't contain any output. But we know the name of the section where the failure occurred, so let's see if we can find out what commands get run in that section by looking at the actual workflow file. We can check that out by clicking "Workflow file" in the lower left.

![A screen capture of the first 30 lines of the workflow file.]({{ "/assets/images/failed_PR/03-workflow-file.png" | relative_url }}){: .align-center}

The full workflow contains over 100 lines, but in this screen capture we can see the part that we care about: Lint Title. Let's give it our full attention:

	- name: Lint Title
		env:
			TITLE: ${{ github.event.pull_request.title }}
		run: npx --no-install commitlint <<< "$TITLE"

I wasn't immediately certain what every single part of this was doing, but with some web searching I was able to verify what I intuited and learn what I hadn't. First, an [environment variable](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-variables) named `TITLE` is being initialized with the [title of our pull request](https://stackoverflow.com/questions/71688092/how-to-get-the-title-of-a-pull-request-with-github-actions). After that, [commitlint](https://github.com/conventional-changelog/commitlint#what-is-commitlint) is being run, and the value of `TITLE` is [being fed into](https://stackoverflow.com/questions/7950268/what-does-the-bash-operator-i-e-triple-less-than-sign-mean) commitlint as input. The `npx` is just a [way of running the commitlint package](https://docs.npmjs.com/cli/v9/commands/npx/?v=true), and the flag `--no-install` is a deprecated form of `--no`, which [suppresses a prompt for input](https://docs.npmjs.com/cli/v9/commands/npx/?v=true).

So in summary, a program called commitlint is doing something — presumably linting! — based on the title of our pull request.

## Linting

In case this is your first time encountering the concept of linting, linting is the process of analyzing text — usually code — to ensure that it meets certain standards. Linting can be used to check functional aspects of code like whether it will actually compile, but it can also be used to enforce a project's stylistic standards related to things like line length, spacing and indentation, etc.

If the title of our pull request is being linted, we'll need to know the rules its being judged by. According to the [commitlint documentation](https://commitlint.js.org/reference/configuration.html), the configuration gets retrieved from one of several different files. It's common for configuration files to be stored in a project's root directory, so let's check to see if one exists:

![A list of files and folders for the project's root directory, with a green arrow pointing towards ".commitlintrc.mjs".]({{ "/assets/images/failed_PR/04-commitlint-config-find.png" | relative_url }}){: .align-center}

Sure enough, a file named `.commitlintrc.mjs` is right where we'd expect it to be. The file contains only 10 lines:

	export default {
		"extends": [
			"@commitlint/config-conventional"
		],
		"rules": {
			"body-max-line-length": [
				0
			]
		}
	}

According to that [configuration documentation](https://commitlint.js.org/reference/configuration.html#configuration-object-example), it looks like this config overrides one rule by setting `body-max-line-length` to 0, but other than that it uses the conventions in `@commitlint/config-conventional`. Thankfully, the top search result for the latter term is the [npm page containing its documentation](https://www.npmjs.com/package/@commitlint/config-conventional), which explains all of the rules our pull request title is being checked against. Armed with these rules, we should be able to figure out where the problems are happening. The title of the pull request was:

	Updated links in README.md's File structure section from .mjs to .ts.

If you want to, as an exercise you can go through the rules on your own to find each of the ways this title is falling short of these standards. While the rules page contains multiple references and links to Conventional Commits, be aware that `@commitlint/config-conventional` contains additional rules that aren't part of Conventional Commits. That said, the [Conventional Commits page](https://www.conventionalcommits.org/en/v1.0.0/) is quite helpful since it explains some of the terminology used in the rules.

So as you may have discovered, our title fails most of the rules related to type and subject. The title should start with one of several pre-approved types, then there should be a colon, then there should be consistent capitalization in accordance with the `subject-case` rule, and finally the title should NOT end with a period. We did successfully abide by the `body-max-line-length: 0` override by not having any body, though!

## Fixing the Pull Request Title

Now that we know what rules we need to follow, we could go fix the title of our pull request. But before we do that, there's one more thing we might want to consider doing: taking a quick look at successful pull requests in this project. By doing this we'll get a better idea of what the norms are for this project, some of which may not be hard-coded into linting rules. To do this, we go to the project's page on GitHub, then click the "Pull requests" tab towards the top of the page. The Pull Requests page will generally start with a filter that only shows open pull requests, but we'll change it to `is:pr state:merged`, which will allow us to see pull requets that were successfully merged into the project.

![GitHub UI showing the pull requests page with the aforementioned filter applied.]({{ "/assets/images/failed_PR/05-view-pull-requests.png" | relative_url }}){: .align-center}

Next, we can finally update the title of our pull request. If we return to the page for our specific pull request, right after the pull request's title there's a number and a pencil icon. By clicking the pencil icon, we can edit the name of our pull request.

![The title of our pull request in the GitHub UI, with the pencil icon at the end.]({{ "/assets/images/failed_PR/06-edit-pr-title.png" | relative_url }}){: .align-center}

The finalized title of the pull request is:

	docs(readme): file structure section .mjs -> .ts

This title meets all of the requirements! So why aren't we done yet? Why are there so many words below this? It's because there's one additional problem that I initially missed. If you looked over some of the documentation I linked, maybe you caught it?

## Fixing the Commit Message

Quite simply, commitlint is a utility that lints commit messages. Yes, the title of our pull request _is_ being fed into commitlint, and it _is_ getting linted. But it's not the only thing getting linted; commitlint is also linting the Git commit message associated with our pull request. And as you might expect, my initial commit message — which was identical to the pull request title — did not meet the linter's standards.

Luckily, we've already done most of the work. We know what to change the commit message to, now we just need to change it.  Because the changes in our pull request are the most recent changes we made to our forked repository, we can do that by following these steps:

1. [Clone](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository) a local copy of our fork.
2. Open a local command window to the base directory of our cloned repository.
3. If our changes were in a [branch](https://www.w3schools.com/git/git_branch.asp), we want to be working in that branch by using the `git checkout BRANCH-NAME-HERE`.
4. Enter the command `git commit --amend`.
5. A text editor will open. In the text editor, edit your commit message.
6. Save and then close the editor. The commit message has now been changed locally.
7. To push this change to our remote fork, use the command `git push --force-with-lease origin BRANCH-NAME-HERE`.
	- If you aren't using a branch or don't know the name of your branch, use `git branch --all`; the text beside the asterisk is what you'll type instead of `BRANCH-NAME-HERE`.

## Resolution

After completing these steps, I went back to GitHub and the commit associated with my pull request had been updated, which was immediately reflected in my pull request as well. I double-checked everything to make sure everything was in order, then requested another review of my pull request by clicking the refresh icon in the upper-right corner of the pull request page.

![The GitHub pull request UI showing reviewers, with a green arrow pointing towards the refresh icon on the right side.]({{ "/assets/images/failed_PR/07-reviewers.png" | relative_url }}){: .align-center}

Later in the day my changes were approved, which triggered a new workflow run. All of the checks passed, and my change was merged into the official project.

![GitHub pull request UI that says "Pull request successfully merged and closed" and underneath it "You're all set — the branch has been merged."]({{ "/assets/images/failed_PR/08-successfully-merged.png" | relative_url }}){: .align-center}

When I first made my pull request, I had only intended to make a simple update to some outdated documentation. But by trying to contribute even in this basic way, I ended up facing unexpected challenges and learning a great deal. I hope that by recording some of that process in this post, it might help someone to find a solution to a similar issue, or perhaps encourage someone to try to make their own contribution to open source.

Thanks for reading!
